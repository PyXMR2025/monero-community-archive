# Original Description
### What
Improves sync-status tracking and peer-disconnect handling.

### Why
The previous implementation inferred sync state from `target_height`, which had several shortcomings:

1. `target_height == 0` conflated `NoPeers` with `Synced`.
2. `get_info.synchronized` has historical "has ever synced" semantics, but that state was not modeled explicitly.
3. Disconnecting the peer with the highest cumulative difficulty could leave the sync status stuck on an old target height.
4. `get_info` read the target height separately for `busy_syncing` and `target_height`, so an update between those reads could produce a conflicting response.
5. When an invalid block caused the blockchain manager to stop the downloader, the syncer returned to waiting instead of rechecking immediately.

`monerod` appears to treat `synchronized` as "has ever synced", so it intentionally remains true after the first sync even if all peers disconnect. It also performs separate sync-state reads, but Cuprate can avoid returning an internally inconsistent response.

### Where
`cuprated`, `p2p-core`

### How
1. Store the current state as `SyncStatus::NoPeers`, `BehindPeers`, or `Synced`, including the target height and cumulative difficulty when behind.
2. Track whether the node has ever synced separately and use that state for `get_info.synchronized` and sync waiters.
3. Add a peer-disconnect callback and wake the syncer when the disconnected peer matched or exceeded the recorded target difficulty.
4. Read `SyncStatus` once in `get_info` and derive both `busy_syncing` and `target_height` from that snapshot.
5. Re-notify the syncer after a downloader stop signal so it rechecks immediately.
