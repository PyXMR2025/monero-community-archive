# Original Description
Note this PR is in collaboration with @selsta.

While running #420 on [this modified branch](https://github.com/j-berman/monero/tree/bf4af1e742403e754bad154fa396a02832babecf), @Rucknium still observed double spend errors after some time. The logs indicate that the strand relaying txs is getting backed up, and duplicate txs get queued for relay in the strand as a result. #420 exacerbates the issue because local txs can get piled up in the relay strand, continuously getting re-dispatched to the strand before the strand executes relaying even one of them (once the tx gets relayed in the strand, it would then prevent the re-relay loop from re-queuing for relay).

@vtnerd is tackling the strand getting backed up separately.

This PR ensures that duplicate txs won't get queued for relay in the strand.

I have a lingering thought that it may be the case that this PR is unnecessary once the strand getting backed up is solved. I'm thinking I will request @Rucknium run this patch with more thorough logging + @vtnerd's patch once ready, so we can see if A) the double spend issue is solved for good, and B) if this PR is actually necessary or not (i.e. if txs are piling up in the strand even after the strand bottleneck is solved).

Here's a helpful log snippet from @Rucknium for reference: 
[bitmonero.log_2026-06-29-23-26-56.tar.gz](https://github.com/user-attachments/files/29976293/bitmonero.log_2026-06-29-23-26-56.tar.gz)

Note how `Going to re-relay local tx <60df75853588a435a59b13a46b3964829606ccb42b938d2c0bb44aaccfc2bc04>` appears in that log file 69 times in relatively short intervals (and is also marked as a double spend in there).
