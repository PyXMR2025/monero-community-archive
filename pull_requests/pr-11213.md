# Original Description
`get_reserve_proof` picks its outputs with `is_spent(td, true)`, which only
counts an output as spent once its spending tx has confirmed. `commit_tx`
marks an output spent as soon as the tx goes to the daemon, well before it
confirms, so an output already used as input to a pending send still passes
as unspent here.

That means a wallet can generate a reserve proof over outputs it has already
committed to spending in an unconfirmed transaction. `check_reserve_proof`
reports them as unspent and available, but they're gone as soon as that send
confirms. This is the same behavior reported with a stagenet repro in #6595.

Switched the selection to `is_spent(td, false)`, matching what the wallet's
own default (non-strict) balance already uses for the same reason. Since
`account_minreserve` indexes into that same `selected_transfers` vector a few
lines down, I also changed its earlier `balance()` guard to sum
`selected_transfers` directly instead: `balance(account, false)` also folds
in the change and self-transfer amounts of our own unconfirmed txs, which
aren't outputs in `m_transfers` yet, so it can report more than
`selected_transfers` actually holds and let that loop walk past the end of
the vector.

Verified: compiled `src/wallet/wallet2.cpp` clean with the project's
`obj_wallet` target (`ninja src/wallet/CMakeFiles/obj_wallet.dir/wallet2.cpp.o`),
release flags, no new warnings. No existing unit tests exercise
`get_reserve_proof` (it needs a live wallet against a daemon), so I traced
the fix by hand against `commit_tx`, `is_spent`, and `balance_per_subaddress`
to confirm the invariant the second loop in the `account_minreserve` branch
relies on (`selected_transfers`' sum is always >= the guard) still holds. I
did not run a full node/wallet integration test.
