# Original Description
When validating that a transaction has some PoW bound to it, either during block sync or [PoWER](https://github.com/monero-project/research-lab/issues/133) we usually use a transaction's TXID to bind that PoW. And transactions are transmitted over the network as opaque byte blobs. The current way that the TXID is calculated from a transaction blob, is that it is A) [deserialized](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_basic.h#L244), then B) [expanded](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L121), then C) the [subsections](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L1367) [are](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L1375) [hashed](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L1385), and finally, D) the final transaction hash is [calculated](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L1389) from the subsection hashes. Ideally, this process should be as quick as possible, so that bad transaction data can be failed as quickly as possible, but in reality, this process is much more expensive than it needs to be.

1. There's one Ed25519 point decompression, variable-base scalar-point multiplication, and point compression in `cryptonote::expand_transaction_1()` *per output* [here](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L170) and [here](https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L194). Each decompress + multiply + compress op is ~100x slower (citation needed) than `crypto::cn_fast_hash()`!!!
2. For a $N$-input `RCTTypeBulletproofPlus` (v6) RingCT transaction, deserializing the transaction takes $2N +10$ memory allocations: 
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_basic.h#L146 ($N$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_basic.h#L187-L189 ($3$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L363 ($1$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L394 ($1$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L447 ($1$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L274-L275 ($2$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L500 ($1$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L511 ($N$)
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/ringct/rctTypes.h#L591 ($1$)
3. Expanding the transaction takes a memory allocation: https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils.cpp#L168
4. Serializing the transaction prefix inside the hashing function takes at least one allocation (`calculate_transaction_prunable_hash()` uses cached `unprunable_size` field instead of serializing):
  - https://github.com/monero-project/monero/blob/4a24ca3ad6f42cb860fd48ee49a4ccd2bbb0ff1b/src/cryptonote_basic/cryptonote_format_utils_basic.cpp#L38

So all told, for a N-in M-out transaction today, the daemon does $2N + 12$ memory allocations, $M$ Ed25519 point decompressions, $M$ Ed25519 variable-base scalar-point multiplications, $M$ Ed25519 point compressions, and 4 Keccak256 hashes, just to calculate the TXID. This is a DoS vector. Without a fork, performant code could reduce this to just the 4 Keccak256 hashes. With a hard fork, keeping the TXID bound to its proof data, we could reduce this to 2 Keccak256 hash, and still retain pruning capabilities. With a hard fork, moving the transaction proof data to a field in the block, we could reduce this to just 1 Keccak256 hash, and still retain pruning capabilities.
