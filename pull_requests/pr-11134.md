# Original Description
`wallet2::shutdown()` only sets a flag, which `refresh` checks between daemon RPC calls. If the current call is blocked on a stalled or unresponsive connection, the shutdown has no effect until the call hits the full RPC timeout (3.5 minutes by default), so shutting down a wallet mid-refresh (ctrl+c on wallet-rpc, or shutting down an embedded wallet) can hang for minutes, blocking progress to restart the wallet or shut down the application.

This PR makes `wallet2::shutdown()` abort any in-flight daemon request by adding `shutdown()` to epee's http client. The epee override is safe to call from any thread. The base class default is a plain `disconnect()` for clients that don't support cross-thread interruption.

The new `shutdown()` just sets an atomic flag and wakes the blocked thread, which fails its request promptly and cleans up its own socket. The client reconnects transparently on next use, and shutdown is a no-op when no request is in flight, so idle connections are untouched. 

As a result, wallets shut down promptly and cleanly.

Release PR: https://github.com/monero-project/monero/pull/11135

Depends on https://github.com/monero-project/monero/pull/11138 (its commit is included here; please review the last commit only).

## thomasbuilds | 2026-08-20T08:33:34+00:00
An abort landing inside this handshake is indistinguishable from "server has no TLS": `handshake()` returns false, this maps to `CONNECT_NO_SSL` (line 188), and with the default `e_ssl_support_autodetect` `connect()` permanently sets `support = e_ssl_support_disabled` (line 230) - every later auto-reconnect is silent plaintext until the next set_daemon, and a MITM can widen the window by stalling handshakes. I suggest checking `shutdown_requested()` after a failed handshake and returning `CONNECT_FAILURE` instead.

## thomasbuilds | 2026-08-20T08:34:43+00:00
This makes `stop()` async-signal-unsafe: `shutdown()` does `boost::asio::post()` (a heap allocation plus the io_context's non-recursive scheduler mutex) and `stop()` runs in real POSIX signal-handler context (simplewallet's ^C during manual refresh via `interrupt()`, wallet-rpc's initial-sync handler). A signal landing on the thread inside `run_one()` or mid-malloc can self-deadlock or corrupt the heap. Pre-PR stop() was only relaxed atomic stores.

## thomasbuilds | 2026-08-20T08:35:36+00:00
This one-shot wait is registered before resolution, so if the deadline fires while `getaddrinfo` is still running, the handler is consumed doing nothing (`resolver_.cancel()` can't stop a started lookup; the socket isn't open yet) and `check_deadline` re-arms to `time_point::max()` - the later `async_connect` (or the v6 fallback resolve) then runs with no deadline and blocks until the OS TCP timeout (~2 min). Related: client destruction joins the resolver worker thread stuck in that same lookup, so teardown after an "aborted" DNS stall still blocks. Pre-PR the resolve was synchronous, so the timer always covered an already-open socket.

## thomasbuilds | 2026-08-20T08:36:45+00:00
```suggestion
    virtual bool shutdown() { return disconnect(); }
```

The description says "the base class default is a plain disconnect()", but this is pure virtual - every out-of-tree subclass (this class is wallet2's injection point) breaks at compile time and will get a do-nothing stub, silently losing the abort there.

## thomasbuilds | 2026-08-20T08:37:53+00:00
```suggestion
    EXPECT_FALSE(error);
```
A transient accept failure here early-returns past the still-joinable `connecting` thread - its destructor calls `std::terminate` and kills the whole test binary. `EXPECT` keeps the `shutdown()`/`join()` below reachable (they complete harmlessly on the error path).
