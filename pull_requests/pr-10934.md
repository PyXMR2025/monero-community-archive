Adds two components to the tests directory:
1. `tests_common` a shared utility library for different types of tests

Also updates the transaction fuzzing test to call `ver_non_input_consensus()` for different HF versions.

OSS-Fuzz downstream PR: https://github.com/google/oss-fuzz/pull/15893

Part of upstreaming Carrot/FCMP++

## thomasbuilds | 2026-08-25T07:36:29+00:00
`ver_mixed_rct_semantics()` has no `hf_version` parameter ([tx_verification_utils.cpp#L394](https://github.com/monero-project/monero/blob/c7d82632577eb94b08f63cb4378faf78b3ef7f05/src/cryptonote_core/tx_verification_utils.cpp#L394)), so every fork that accepts the transaction re-runs the full range proof verification. On the checked-in TX2 (RCTTypeSimple, 2 inputs, 2 outputs), hard forks 4 to 8 each spend 10-13 ms in the same `verRctSemanticsSimple()` call. The total is 55-57 ms per exec in a native build and about 115 ms in an oss-fuzz-style libFuzzer build, compared with about 1 µs and 0.1 ms respectively before this change. The five RingCT seeds this PR generates cost 8-60 ms per exec for the same reason. In 30-second libFuzzer sessions, a corpus of the 10 generated seeds goes from about 310k runs to 16-32k, and a TX2-only corpus from about 300k to 6-14k. libFuzzer's `-report_slow_units` defaults to 10 seconds, so none of this is ever reported. The target also starts an nproc-1 threadpool now, because `verRctSemanticsSimple(rv)` delegates to the batch overload ([rctSigs.cpp#L1480](https://github.com/monero-project/monero/blob/c7d82632577eb94b08f63cb4378faf78b3ef7f05/src/ringct/rctSigs.cpp#L1480), [#L1352](https://github.com/monero-project/monero/blob/c7d82632577eb94b08f63cb4378faf78b3ef7f05/src/ringct/rctSigs.cpp#L1352)).

Suggestion: verify one fork per exec and take the fork from the input, for example a leading selector byte. `gen_corpus` can emit that byte because it knows which fork each seed was built for, and TX1/TX2 would need one byte prepended once. All 16 forks remain covered, across execs rather than within each one.

There is no iteration cap, and for some combinations of reward and hard fork this loop provably never terminates. The next state depends only on `cumulative_tx_weight`, `fee`, `current_block_weight`, `r` and the weight and output sum of `tx`, and tracking that state finds repeats: a reward of 1e11 at hard forks 5 to 14 repeats with period 181, 0.5 XMR cycles at forks 4, 15 and 16, 0.7 XMR at forks 2 and 3, and rewards of 0, 1, 1e6 and 1e9 cycle at every fork (15 of 320 cells over 0.1 to 2.0 XMR at all 16 forks). The 2 COIN reward that `gen_corpus` uses converges everywhere, so this does not bite today, but as a shared helper it should fail loudly, for example `CHECK_AND_ASSERT_THROW_MES(++iterations < 10000, "coinbase reward adjustment did not converge");`
