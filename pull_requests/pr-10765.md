# Original Description
This (finally) implements support for Polyseed as created by @tevador in `wallet2`, the Wallet API, the CLI wallet app and the wallet RPC server.

Substantial parts come, with some changes, from [this patch](https://github.com/MrCyjaneK/monero_c/blob/develop/patches/monero/0007-polyseed.patch) authored by @tobtoht and refined by @MrCyjaneK for the [monero-c](https://github.com/MrCyjaneK/monero_c) library. As part of that library the code from that patch is in active use in a number of third-party wallet apps for quite a while now.

The code in `simplewallet` for the CLI wallet app and in `wallet_rpc_server` is my work.

A bug regarding the patch in connection with background sync of Polyseed wallets that I learned about from a discussion in a Matrix channel (the seed info gets lost) is corrected in a clean way now.

It may be that the Polyseed methods in the Wallet API are still quite basic and not yet sufficient to implement really comprehensive support in an app like the Monero GUI wallet app, but without actually trying it's hard to find out what's missing, if anything, and I did not try to go beyond what said patch already brings.

## tobtoht | 2026-06-19T14:16:07+00:00
I'd definitely prefer not to add a new third-party dependency if we can avoid it (especially not on a C library).

We could have Polyseed not do unicode normalization. We don't do this for legacy seeds (even though we should) and this hasn't resulted in any bug reports in the span of a decade (that I know of). This approach requires changes to the Polyseed library. It seems like the lazy route and is technically not correct. 

(Do people just not use seeds in other languages? I find it curious that we haven't seen more issues reported with legacy seeds. Related: BIP39 [strongly recommends against](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki#wordlists) using non-English wordlists.) 

Given the relatively narrow subset of unicode we actually need for this, we could attempt to implement the mappings ourselves. On second thought, I have no idea how hairy normalization gets for Chinese, Korean, etc. It's something I'd like to explore in the future to get a better understanding of.

Neither alternative feels particularly enticing though, so I think adding `utf8proc` for now is fine.

## selsta | 2026-07-15T20:46:23+00:00
Previously the layout was:

```
bytes 0–31:   spend key
bytes 32–63:  view key
bytes 64–95:  first multisig key
```

This change inserts `m_polyseed` before the multisig keys:

```
bytes 0–31:   spend key
bytes 32–63:  view key
bytes 64–95:  Polyseed
bytes 96–127: first multisig key
```

Consider an existing wallet. Its first multisig key was encrypted as:
```
ciphertext = multisig_key XOR keystream[64..95]
```

When the new code opens that file, it decrypts the same ciphertext using `keystream[96..127]`:
```
result = ciphertext XOR keystream[96..127]
```

That result is not the original multisig key.

There is no version check or migration path selecting the old layout. The spend and view keys remain correct because their offsets did not change. The multisig secret keys are not validated during loading, which hides the problem until they are used. If the wallet is rewritten those incorrect keys are saved using the new layout.
