# Original Description
## Why [StageX](https://stagex.tools/) over Guix

- Guix upstream is much slower to update packages.
- Container engines ship with AppArmor/SELinux profiles. No issues with unprivileged user namespaces.
- Container engines run on more Linux distributions.
- Registries like docker.io are more reliable than Guix substitute servers.
- StageX images are multi-party-signed. Less risky than trusting Guix substitutes.
- Build system configuration in Containerfiles/shell instead of a lisp dialect.
- We don't have to trust a single driver. StageX release builds can support any container engine.
- We have more control of what ends up in our build environment. Down to the file level.
- Builders are more likely to already have Docker or podman installed.
- More off-the-shelf OCI tooling available. Easier debugging and caching.
- FHS instead of `/gnu/store`.

## Building

### 0. Requirements

- x86_64 Linux environment
- 50GB of free space

### 1. Install docker or podman

 **Docker**

Installation instructions: https://docs.docker.com/engine/install/

If you have an existing installation, make sure it supports buildx:

```bash
docker buildx version
```

**Podman**

 Installation instructions: https://podman.io/docs/installation#installing-on-linux

You may need to add: `unqualified-search-registries = ["docker.io", "quay.io"]` to `/etc/containers/registries.conf`

### 2. Run a build

**Docker** 

```bash
make stagex-build
```

**Podman**

```
CONTAINER_ENGINE=podman make stagex-build
```

### 3. Get hashes

```bash
make stagex-hashes
```

## Debugging

If you made changes to the source for testing purposes, you can start a build with:

```bash
FORCE_DIRTY_WORKTREE=1 make stagex-build
```

To interactively debug a build:

```bash
INTERACTIVE=1 make stagex-build
```

To build for a specific target:

```bash
HOSTS="arm64-apple-darwin" make stagex-build
```

To limit the number of build threads:

```bash
JOBS=N make stagex-build
```

If something went wrong, and you want to start over:

```bash
rm -rf stagex
```

## Why static [musl](https://musl.libc.org/)+[mimalloc](https://github.com/microsoft/mimalloc) over dynamic glibc

We get fully static release binaries that run on pretty much any Linux distribution, at less complexity and binary weight than statically linking glibc.

Compared to gitian/guix release binaries, these also run:

- On distributions with old versions of glibc (< 2.27)
- On musl-based distributions (like Alpine)
- On non-FHS distributions (like Nix and Guix System)
- In a `termux-chroot` on Android
- In `FROM scratch` containers

mimalloc performs better at checkpointed blockchain synchronization and has a lower memory footprint than glibc, see results in the next section.
