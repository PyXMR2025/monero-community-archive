# Original Description
The `create_address` bumps the wallet's in-memory subaddress index and returns the new address immediately. The updated index is not written to the wallet keys file until the next store().. which happens on its own schedule (store RPC call, clean shutdown..), not tied to the address-creation call itself.

This means a caller can receive an address from `create_address`, treat it as valid and start directing funds to it, and have that address effectively "disappear" from the wallet's perspective if the process terminates (crash, OOM kill, power loss..) before the next persist. On restart, the index has not advanced, and the next create_address call reissues an index that was already handed out and may already be in use elsewhere in a caller's system.

Please add an optional parameter (or startup flag) that makes the RPC call block until the new address/index has been durably written to the wallet file before responding.

(Arguably this should be the default, but making it opt-in avoids any behavior/performance change for existing callers.)

## napoly | 2026-09-10T09:03:04+00:00
Following up from PR #11275 (closed).. wanted to bring the durability discussion back to this issue since it's the root problem..

Any wallet state change should be properly persisted before returning a result to the caller, not just address creation.. Otherwise the wallet is exposed to the same class of bug across every mutating RPC call, not just `create_address`, and breaks basic ACID guarantees.

On the suggestion to just call `store` separately over JSON-RPC (double call is resource heavy).. see [jeffro256's comment here](https://github.com/monero-project/monero/pull/11275#issuecomment-5607548890): that pushes the durability guarantee onto the caller, which is problematic.. The caller would then need to treat "mutate" + "store" as one **atomic** operation and roll back properly if `store` fails. But if, for example, a customer has already sent funds to an address that wasn't actually persisted, there's no clean way to roll that back.. the money's already moved.. a two-call approach just relocates the race condition rather than closing it..
