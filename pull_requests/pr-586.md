# Original Description
### What
Depends on pt1, PR #585

Building on part 1, this replaces the panic-on-error patterns in cuprated's services with error propagation that makes use of the graceful shutdown mechanism

### Why
So we dont panic and insta-crash upon a error, shutdown should be graceful. Internal errors still caused panics before this via PANIC_CRITICAL_SERVICE_ERROR

### Where
`cuprated`:
- `monitor.rs` - `spawn_critical` added to `TaskExecutor`: logs and triggers shutdown on `Err`, panic, or `Ok(())`.
- `constants.rs` - `PANIC_CRITICAL_SERVICE_ERROR` / `CRITICAL_SERVICE_ERROR` collapsed into one constant.
- `blockchain/error.rs` (new) - `IncomingBlockError` typed enum with error variants, `From` impls + `is_peer_fault()` to determine bannable behaviour
- `txpool/error.rs` (new) - `IncomingTxError` same shape
- `blockchain/manager/handler.rs` - `.expect(...)` -> `?` throughout; functions return `Result<_, IncomingBlockError>`; empty-batch errors instead of panicking; `# Panics` -> `# Errors`.
- `blockchain/manager.rs`, `blockchain.rs` - `spawn_critical` for run loops; `check_add_genesis` returns `Result`.
- `txpool/manager.rs` - `.expect` -> `?`; `TxPoolManagerHandle::new_block` returns typed `Result<(), TxPoolManagerClosed>`.
- `txpool/incoming_tx.rs` - `IncomingTxHandler::init` returns `Result`.
- `tor.rs` / `p2p.rs` - runtime `panic!`s in `transport_*_config` and `initialize_clearnet_p2p` / `start_tor_p2p` replaced with `Result`.
- `rpc/server.rs` - `init_rpc_servers` returns `Result`; server spawn uses `spawn_critical`.
- `rpc/handlers/{helper,json_rpc,other_json}.rs` - coinbase/hardfork/`flush_cache`/`serde_json` panics -> `Result` returns.
- `lib.rs` - `?` propagation through `Node::launch` and the post-sync Tor zone spawn.

`cuprate-types`:
- `TxConversionError` re-exported

### How
`spawn_critical` wraps each subsystem's future: if it returns an error it is logged and the shutdown token is hit, triggering the same graceful shutdown path as OS signals.

Critical tasks returning `Ok(())` also trigger shutdown.

Validation errors (invalid blocks/transactions from peers) are distinguished from service errors (database/internal failures) using simple enums (`HandleBlockError`, `HandlerError`). Only service errors propagate to shutdown - validation errors are handled gracefully (ban peer, cancel downloader, etc.)
