# Original Description
In `--restricted-zmq-rpc` mode, the ZMQ `get_transaction_pool` method returns real `receive_time` and `last_relayed_time` for every pool tx. The HTTP equivalent zeros both fields for restricted callers. The ZMQ handler has no restricted check and the method is missing from the ZMQ blocklist.

Verified on `master` @ `4a24ca3ad`.

## Where

ZMQ handler — no `m_restricted` branch, calls `get_pool_for_rpc` directly:
`src/rpc/daemon_handler.cpp:757-763`

ZMQ blocklist — 9 entries, `get_transaction_pool` not among them:
`src/rpc/zmq_restricted_methods.cpp:42-52`

`get_pool_for_rpc` — sets timing fields unconditionally:
`src/cryptonote_core/tx_pool.cpp:1280-1282`

HTTP equivalent — zeros the same fields when not sensitive:
`src/cryptonote_core/tx_pool.cpp:1228-1231`,
`src/rpc/core_rpc_server.cpp:1709-1717`

## Impact

`receive_time` / `last_relayed_time` per node are the canonical inputs to first-spy-estimator deanonymization. A spy aggregating these from public
restricted-ZMQ nodes can correlate per-tx arrival across vantage points - exactly what `--restricted-zmq-rpc` is supposed to prevent.

Both paths already filter to `relay_category::broadcasted`, so stem-phase txs are not exposed. The leak is the timing metadata of broadcasted txs.

Severity per project rubric: **MEDIUM**.

## Fix

Add `"get_transaction_pool"` to the restricted blocklist:

```diff
--- a/src/rpc/zmq_restricted_methods.cpp
+++ b/src/rpc/zmq_restricted_methods.cpp
-    constexpr std::array<std::string_view, 9> blocked_in_restricted_mode{{
+    constexpr std::array<std::string_view, 10> blocked_in_restricted_mode{{
       "flush_txpool",
       "get_peer_list",
+      "get_transaction_pool",
       "mining_status",
       "relay_tx",
```

Plus the matching `EXPECT_TRUE` in `tests/unit_tests/zmq_rpc.cpp`.
