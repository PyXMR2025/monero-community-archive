# Original Description
While building Monero 0.18.4.1 from the official release tarball (without Git submodules), the build fails with:

`ld: cannot find -lwallet-crypto: No such file or directory`

This happens because the target wallet-crypto does not exist in the tarball or build system. However, the correct static library that is built is libcncrypto.a.

The file src/device/CMakeLists.txt incorrectly links against wallet-crypto. To fix the issue, replace the reference with cncrypto:

`sed -i 's/wallet-crypto/cncrypto/' src/device/CMakeLists.txt`

This is required for successful builds using the release tarball without relying on Git submodules. Please fix this in the next tagged release to avoid breaking downstream packaging.

Patch is attached. Tested and confirmed working on Gentoo and macaroniOS (cross-compiling with GCC 13.3.0 and Ninja). Please include this fix in future releases to ensure compatibility outside the monero git clone with submodules.

[monero-0.18.4.1-unbundle-dependencies.patch](https://github.com/user-attachments/files/21548110/monero-0.18.4.1-unbundle-dependencies.patch)

## munzzyy | 2026-07-15T03:37:04+00:00
On current master `wallet-crypto` is a real CMake target, defined in src/crypto/wallet/CMakeLists.txt - `add_library(wallet-crypto ALIAS cncrypto)` when MONERO_WALLET_CRYPTO_LIBRARY resolves to "cn" (the default when no accelerated backend is detected), or a proper library built from the selected backend otherwise. That file is a tracked source file, not part of any submodule, and it's already present at the v0.18.4.1 tag too (checked with `git show v0.18.4.1:src/crypto/wallet/CMakeLists.txt`). `src/crypto/CMakeLists.txt` pulls it in via `add_subdirectory(wallet)` before `src/device` is added, so the target should exist in a normal single-tree CMake build regardless of whether submodules are checked out, since the default "cn" backend doesn't need supercop.

The attached patch (`s/wallet-crypto/cncrypto/` in src/device/CMakeLists.txt) would silently drop the accelerated backend for the device target on anyone building with `-DMONERO_WALLET_CRYPTO_LIBRARY=<something other than cn>`, since cncrypto is the plain fallback implementation. Given the official source tarball apparently hits the same error, this smells more like something specific to how the Gentoo ebuild invokes cmake (a partial/staged configure, or this subdirectory not being reached for some other reason) than an actual gap in the CMake graph. Might be worth checking how the ebuild configures the build before taking the sed patch as-is.
