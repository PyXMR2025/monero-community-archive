# Original Description
Stores a 1 byte field in the mempool meta, `nic_verified_hf_version` which
specifies for which HF version this tx has passed `ver_non_input_consensus()`.
This is checked while handling both alt chains and main chains, and thus allows
us to skip the expensive full mempool revalidation on fork change.

Resolves #10142

Depends on #10915

## thomasbuilds | 2026-09-15T11:58:03+00:00
With `--zmq-pub`, `switch_to_alternative_blockchain()` adds the alt blocks one by one, each `handle_block_to_main_chain()` ends in `send_miner_notifications()` and lands here at a height lower than the one the pool txs were accepted at. A relayed tx whose youngest ring member or coinbase input sits at the 10-block or 60-block boundary fails `check_tx_inputs()` there, gets deleted, and the alt block containing it then fails with "unknown transaction" (alt blocks are added with an empty supplement); the node stays on the losing chain until a peer re-delivers the blocks. Any reorg of depth >= 2 can trigger it.

"Not ready" is transient by nature (height-dependent rules, `pop_blocks`), so deferring the cleanup does not fix it; better not to delete here at all and cache NIC failures instead (see the comment in `is_transaction_ready_to_go()`).

## thomasbuilds | 2026-09-15T11:58:03+00:00
A failure is only remembered as `last_failed_id` for this tip, so a failing tx is parsed and put through `ver_non_input_consensus()` again on every block. Kept-by-block txs (alt-block supplements, popped blocks) stay for 7 days, and an alt block at a pre-fork height can fill the pool with them without fee or weight limits, which makes it per-block range-proof work on every mining/zmq node after a fork. A NIC failure is permanent for a fork version: a `nic_failed_hf_version` byte from the padding, checked before verifying, closes it.

Also, failed txs never trigger the early exit of the backlog loop, so after a fork that invalidates most of the pool the first `get_block_template_backlog()` call verifies the whole pool under both locks.

## thomasbuilds | 2026-09-15T11:58:03+00:00
`return_txs_to_pool()` now passes the stored version, so `add_tx()` drops a returned tx that fails NIC at `hf_version` ("Failed to return taken transaction"), where `(hf_version, hf_version)` always re-added; for a kept-by-block tx whose version legitimately differs that discards something a later reorg may need. Setting `std::get<3>(txs_meta.back()) = hf_version` after a successful re-check here also avoids verifying it again on return.

## thomasbuilds | 2026-09-15T11:58:03+00:00
Without this sweep, nodes that never build templates keep NIC-invalid txs for 3 days after a fork, list them in `get_transaction_pool`, and `get_relayable_transactions()` keeps re-relaying them (fluff txs are re-sent with back-off for 1.5 days, no validity check); peers that no longer have them (the ones that build templates) verify and drop the connection. Skipping relay for txs whose cached version differs and which fail re-verification, or an incremental purge from `on_idle()`, would cover it.
