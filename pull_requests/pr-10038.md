## earnifysu | 2026-07-29T06:29:37+00:00
> It shouldn't affect security AFAIK because Keccak isn't susceptible to length extension attacks, but please correct me if wrong.

length extension is not the issue, keccak is fine there. but there is a concrete effect, and it is closer to what @SChernykh meant by "a piece of data that gets erased by including only the tree root hash".

`tree_hash` carries no length prefix at any level (`src/crypto/tree-hash.c:77-104`). so the tree root does not commit to the leaf count, and with the varint gone the hashing blob does not either.

concretely: for any leaf count `n >= 3`, collapsing exactly one adjacent leaf pair into its hash gives `n - 1` leaves with a byte identical root. the pair is not arbitrary, it is the one at index `2*tree_hash_cnt(n) - n`, which is precisely where the pairing loop at `tree-hash.c:91` starts. i compiled the in-tree `tree_hash` and enumerated it:

| leaves | collapsible pair index | result |
|---|---|---|
| 3 | 1 | -> 2, same root |
| 4 | 0 | -> 3, same root |
| 5 | 3 | -> 4, same root |
| 6 | 2 | -> 5, same root |
| 7 | 1 | -> 6, same root |
| 8 | 0 | -> 7, same root |
| 12 | 4 | -> 11, same root |

so for a v17 block `B` with `tx_hashes = {a, b}`, the block `B'` with the identical header, identical `miner_tx` and `tx_hashes = {H(a||b)}` has the same tree root, and since `get_block_hashing_blob` (`cryptonote_format_utils.cpp:1440-1448`) no longer appends the count, the same hashing blob, the same block id, and the same randomx hash and commitment.

**scope, to be clear about what this is not.** `B'` is not acceptable: it needs a real transaction whose txid is `H(a||b)`, and it shares `B`'s id so `have_block` (`blockchain.cpp:4530`) rejects it once `B` is on chain. i am not claiming an attack and i have not found a way to turn this into one. i also checked the in-tree consumers: `tree_branch` and `is_branch_in_tree` are referenced only by their declaration, their definition, and `tests/unit_tests/crypto.cpp`, so nothing in tree rebuilds a root from a branch and breaks.

what does change is an invariant. before v17 the block id pinned the number of leaves. after v17 it does not, and the hashing blob alone can no longer distinguish those two leaf vectors. that is a property external tooling could reasonably have been relying on, which seems to be the substance of the disagreement here rather than the display value question.

if the goal is a fixed size blob and the invariant is worth keeping, folding the count into the content hash rather than appending a varint to the blob gets both: hash the tree root together with the leaf count, and the blob stays at the three fields `docs/BLOCK_HASHING.md:47-52` describes, with no varint and no 76 vs 75 byte change for pools. that would also leave `tree_hash` itself untouched.

no opinion from me on whether the field should go. just answering the "correct me if wrong" directly, since the answer turned out to be neither length extension nor nothing.
