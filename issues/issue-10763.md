# Original Description
## Problem

`--ban-list` accepts only a local file path. During `init()` (src/p2p/net_node.inl) the node verifies the path, reads the file, and parses one entry per line (IPv4 address or subnet, with `#` comments).

To track a maintained remote list such as https://gui.xmr.pm/files/block.txt, an operator has to download the file manually, store it locally, and repeat that whenever it changes. Pointing the flag at the URL directly would let the node fetch the current list on every startup with no manual step.

## Proposed change

Allow `--ban-list` to accept an `http://` or `https://` URL in addition to a file path. When the value is a URL, the node fetches the list once at startup, validates the response, and parses the body with the same parser used for local files. A local path behaves exactly as it does today.

Semantics kept consistent with the current file behavior:

- Fetched once at startup, not on a timer.
- Failure to obtain a usable list is fatal, matching the current behavior for a missing or unreadable file. This covers connection errors, a non-200 response, an empty body, and a body above a fixed size cap.
- For `https`, the TLS certificate is verified against the system CA store. An operator-supplied URL has no signed payload or DNS hash quorum, so certificate verification is the integrity check.
- Per-line parsing and the handling of invalid lines are unchanged.

This is the minimal version. It could later be extended to refresh the list periodically while running, giving a dynamic ban list without a restart. That is out of scope for this proposal and noted only as a possible follow-up.

## Related work

- #10595 adds URL downloading for the DNS blocklist, verified against a hash quorum in DNS. It targets the automatic blocklist, not the `--ban-list` flag, and uses a different trust model. This proposal does not change it.
- #10747 fixes IPv4 subnet arithmetic in the ban primitives this parser calls. Complementary.
- #9591 renames blocklist to banlist. Naming would follow whatever is current at implementation time.

## Questions

- Is loading `--ban-list` from a URL in scope, or should remote lists stay limited to the DNS blocklist?
- Size cap value. #10595 uses 10 MiB, and reusing it keeps both paths consistent.

Noting a pre-existing limitation in the ban list parser, separate from the URL feature itself but worth tracking as a possible follow-up.

The current `--ban-list` parser (`src/p2p/net_node.inl`, via `src/net/parse.cpp`) handles IPv4 addresses, IPv4 subnets, and single IPv6 addresses, but not IPv6 subnets or CIDR ranges. `net::get_ipv4_subnet_address` is IPv4 only, and `block_subnet` accepts only `ipv4_network_subnet`, so a line such as `2001:db8::/32` is rejected and logged as invalid. Single IPv6 hosts such as `2001:db8::1` already work, since `net::get_network_address` parses them and `block_host` accepts an `ipv6_network_address`.

This is unrelated to loading from a URL: the URL path reuses the existing parser unchanged, so behavior is identical to a local file. IPv6 subnet support would be a distinct change (a new `get_ipv6_subnet_address` plus an IPv6 subnet block path) and should be its own issue and PR if there is interest.
