# Original Description
There's been some concerns about defacto block limits in the serialization code. The tl;dr is that there is a 100 MB limit cap on all p2p messages, 16,383 tx limit (~24.5 MiB) in epee decoding (not-pruned), and 8,190 tx limit (~2.9 MiB) in epee decoding (pruned). Both of the epee limits _typically_ hit before the 100 MB cap, but it depends on the average tx size. The rough block size numbers for epee limits are based on the smallest average tx size possible.

### Issues
The primary issue with large blocks is that someone attempting a blockchain sync via pruning will reject blocks that the network has already accepted. This is due to the object "field" limits in the epee decoder; each pruned tx requires 2 fields thus halving the max txes allowed.

### Mitigations

#### Existing Decoder
I initially thought it was possible to track `vector<std::string>` blob size in the current epee decoder such that the block limit would be effectively removed (in this portion of the code). Due to the pruned tx case, this is not possible (or at the very least, rather complicated). In other words, I likely can remove the epee decoder limits for nodes doing a full-sync or nodes at the chain-tip, but any node attempting a sync via pruning will eventually reject those blocks.

#### "New" Decoder being proposed
The new decoder I proposed is DOMless, and as such "knows" its location in the object tree when unpacking. This allows it to verify minimum blob sizes for the pruned tx + hash, such that the unpacked result is at most ~4x more in memory. The downside is that the code needs review, and is risky as it could result in a bug regression.

### Further Thoughts
Will be documented here in replies as I come up with them.

## jeffro256 | 2026-07-09T21:18:00+00:00
Here are the raw byte size minimums for valid Monero transaction prefixes (does not include surrounding epee binary object with field name):

### Non-coinbase: 41
- version: 1
- unlock_time: 1
- vin size: 1
- txin_v tag: 1
- txin_to_key amount: 1
- txin_to_key key_offsets size: 1
- txin_to_key key_offsets ref 0: 1
- txin_to_key k_image: 32
- vout size: 1
- extra size: 1

All non-coinbase txs must have at least 1 `txin_to_key` input. For v1 txs, no outputs are required AFAICT; the remaining sum is interpreted as the fee.

### Coinbase: 7
- version: 1
- unlock_time: 1
- vin size: 1
- txin_v tag: 1
- txin_gen height: 1
- vout size: 1
- extra size: 1

All non-coinbase txs must have exactly 1 `txin_gen` input. Before v13, a coinbase transaction needn't claim all of the block reward, so it is valid for some coinbase transactions to have no outputs.

`sizeof(cryptonote::transaction)` is 496 on my machine. This means that a legit compression ratio for `cryptonote::transaction` could be up to 12x and 71x for non-coinbase and coinbase txs, respectively. I listed prefix sizes, pruned transaction sizes will be either a couple bytes bigger (v2), or a lot lot bigger (v1).
