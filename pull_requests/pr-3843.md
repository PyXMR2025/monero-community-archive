# Original Description
PCoin (PCN) is a Bitcoin Core v29.4 fork with proof-of-work replaced by RandomX. The hash function, cache and dataset are stock — only the **input** differs — so this reuses the existing RandomX backend and adds nothing to it. **+76 / −2 across 6 files, CPU only.**

`rx/yada` is the closest precedent in this tree and this is the same shape of change.

### The four differences, and why each is explicit

Each fails *silently* if left out — the miner looks healthy and produces nothing — which is why none is folded into a generic path.

| | |
|---|---|
| **Nonce offset 76, not 39** | PCoin hashes the canonical 80-byte Bitcoin header; the nonce is a `uint32` LE at 76. At the CryptoNote default of 39 the nonce lands *inside the merkle root*: hashrate looks normal and not one share is ever valid. |
| **Fixed 16-byte key, so no `seed_hash`** | The key is the ASCII string `PCoin/RandomX/v1` and never rotates, so the pool sends no `seed_hash` and the generic `RANDOM_X` gate rejects every job with code 7 — log in, receive work, discard all of it. |
| **Big-endian 32-byte target** | The share test compares the top 64 bits, so the most significant 8 target bytes are taken. Built by hand rather than reusing the existing 32-byte case, which reads them as a native **LE** `uint64` because Monero sends LE. Backwards here is wrong by ~2^64 with identical logs. Truncating downward only makes the local test stricter — no false accepts. |
| **OpenCL disabled for it** | Left enabled it inherits the generic `rx` profile, then compiles a kernel with an ALGO id no `.cl` defines. An undefined identifier in an OpenCL `#if` evaluates to 0, so it fails as a confusing kernel-build error instead of a clean "unsupported". |

`setSeedRaw()` takes the raw 16 bytes and deliberately does **not** pad or re-hash to 32: `randomx_init_cache()` is length-sensitive and a padded key silently produces a different cache. `RxCache::init()` early-returns on an unchanged seed, so the cache is built exactly once — no seed height, no dataset transition, no two-VM boundary of the kind Monero needs every 2048 blocks.

### Tested against the live network, not only compiled

Built from this branch on Debian 13 (gcc, Release, `-DWITH_OPENCL=OFF -DWITH_CUDA=OFF`), then pointed at the public pool:

```
 * POOL #1      pool.pc.am:3333 algo rx/pcoin
net      use pool pool.pc.am:3333  178.105.178.27
net      new job from pool.pc.am:3333 diff 312389 algo rx/pcoin height 7420
randomx  init dataset algo rx/pcoin (16 threads) seed 50436f696e2f5261...
randomx  allocated 2336 MB (2080+256) huge pages 100% 1168/1168 +JIT (243 ms)
randomx  dataset ready (2203 ms)
miner    speed 10s/60s/15m 624.1 628.4 n/a H/s max 663.7 H/s
cpu      accepted (1/0) diff 19524 (174 ms)
```

The seed reads `50436f696e2f5261...` — `"PCoin/Ra..."` — and **the pool accepted the share**, which only happens if the nonce offset and the target parsing are both correct. All three aliases resolve: `rx/pcoin`, `randompcoin`, `randomx/pcoin`. No new warnings in the touched files.
