# Original Description
`estimate_rct_tx_size()` and `estimate_tx_weight()` compute the Bulletproof padded output count with `while ((1<<log_padded_outputs) < n_outputs)`, shifting a signed int. For `n_outputs > 2^30` this reaches `1 << 31` (signed overflow, UB), and once the shift count exceeds the int width the value cycles and never reaches n_outputs, so the loop never terminates. `estimate_tx_size_and_weight()` accepts `n_outputs` up to INT_MAX (only negative is rejected), so a single wallet-rpc call spins the handling thread forever.

## selsta | 2026-08-25T18:46:14+00:00
What's the origin of `0xffff`?

## Masamuneee | 2026-08-26T02:23:13+00:00
`0xffff` isn't a protocol constant, just a generous sanity bound. The `UINT64_C(1) << change` is the loop fix; the `> 0xffff` guards also stop the linear int terms (`n_inputs * …`, `n_outputs * (6+32)`) from overflowing. 65535 is far above any tx (max 16 outputs), so it constrains nothing. Can swap for a named constant if you prefer.

## selsta | 2026-08-26T14:02:33+00:00
Did you check for pre bulletproof transactions? AFAIK they allowed for more than 16 outputs.

## Masamuneee | 2026-08-28T03:19:38+00:00
I have checked it and shouldn't have said 16. It is only the Bulletproof/BP+ aggregation cap; pre-bulletproof and pre-RingCT txs had no such limit, only tx/block weight, so they could exceed 16 outputs. Rather than rely on a bound at all, I've dropped the` 0xffff` and cast the linear size terms to `size_t`, so the estimate stays overflow-safe for any count with no magic number and no artificial output cap.
