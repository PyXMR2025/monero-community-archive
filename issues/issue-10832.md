# Original Description
Hi Monero devs/community,

I am trying to understand whether a recent Beldex incident has any security relevance to Monero, since Beldex is a Monero/CryptoNote-derived codebase but has substantial additional consensus logic.

Beldex published a network update on 2026-06-27 stating that, at approximately 2026-06-26 08:45 UTC, an anomalous block at height 5518800 generated an incorrect masternode reward.
The expected reward was 6.25 BDX, but the affected validator/masternode reward was approximately 900,018,906.34 BDX.
Beldex initiated an emergency hardfork and rolled the canonical chain back to height 5518799.
Their v7.0.2 release includes “Fix: Coinbase overspend” and HF21 activation around that rollback height.
Relevant public references:

Beldex incident post: https://beldex.io/blog/beldex-network-update-hardfork-21
Beldex v7.0.2 release: https://github.com/Beldex-Coin/beldex/releases/tag/v7.0.2
Beldex issue #188: https://github.com/Beldex-Coin/beldex/issues/188
Beldex PR #189: https://github.com/Beldex-Coin/beldex/pull/189
Beldex PR #200: https://github.com/Beldex-Coin/beldex/pull/200
My current understanding:

The Beldex bug appears related to Beldex-specific reward splitting and consensus additions: masternode rewards, governance outputs, and PoS/PoW fallback behavior.
The Beldex fix removed a hardfork guard from the coinbase overspend check. Before the fix, the reward cap check looked gated behind a condition like version > hf::hf20_bulletproof_plus, which could be unreachable if HF20 was the highest deployed enum value.
In current Monero master, Blockchain::validate_miner_transaction appears to compute money_in_use, calculate base_reward via get_block_reward, and reject base_reward + fee < money_in_use; for current hardforks it also rejects non-exact coinbase rewards.
Questions:

Is my understanding correct that Monero does not share the specific Beldex risk because Monero does not have Beldex's masternode/governance/POS-fallback reward paths?
Is there any analogous Monero consensus path where the coinbase reward cap check is conditional on a hardfork version in a way that could become unreachable or incorrectly disabled?
Are there tests or invariants in Monero that specifically assert that the sum of coinbase outputs can never exceed get_block_reward(...) + fees across all active and future hardfork versions, including tail emission and block weight penalty cases?
Was any of the Beldex reward-splitting logic derived from old Monero code in a way that Monero maintainers think is worth double-checking, or is it clearly Beldex-specific?
I am not asking for exploit details. I am trying to verify whether this incident has any implications for Monero node operators/exchanges, or whether it should be treated as a Beldex-specific consensus modification issue.

Thanks.



# Discussion History
## thomasbuilds | 2026-06-28T06:13:15+00:00
This is Beldex-specific. The Beldex defect gated the coinbase overspend cap behind `version > hf::hf20_bulletproof_plus`, the highest enum value (`hf_max`), so for every live block the condition was false and the cap was dead code.

Monero's equivalent check in [`validate_miner_transaction`](https://github.com/monero-project/monero/blob/master/src/cryptonote_core/blockchain.cpp#L1412) has no version guard:

```cpp
if(base_reward + fee < money_in_use) return false;
```

It is unconditional and runs whenever a block is added to the main chain, including reorgs.
Monero also has none of the masternode/governance/PoS reward-splitting that Beldex misgated so there's no extra reward component that could escape the cap.
