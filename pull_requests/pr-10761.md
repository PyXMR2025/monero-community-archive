# Original Description
### Overview

Wallets call the `/getblocks.bin` endpoint in a loop, which returns any new blocks or pool txs since the wallet last requested. However, if the chain hasn't advanced blocks, the daemon could no-op and *not* return anything (see "quick check for noop").

### Before this PR

Before this PR, because the daemon hasn't advanced blocks, the daemon would skip returning pool txs inside the `get_pool` for the incremental pool fetching approach (since it would immediately return true when handling the no-op case). [Stressnet] wallet2 would then fallback to the non-incremental approach for pool fetching, which takes multiple rounds.*

### After this PR

The daemon still continues on to the `get_pool` incremental handling even if the daemon hasn't advanced any blocks past the wallet's sync height. The wallet therefore correctly uses the incremental pool fetching logic in this case.

Truthfully, I'm not sure how we missed this when testing incremental pool fetching in the past. I thought I tested this exact circumstance pretty extensively on different occasions, but I may have missed something, or the issue doesn't surface with a release wallet2 wallet. I observed this issue on stressnet when testing #10605.

### Why this PR is so big

It's copying almost every existing line exactly the same, but pulls out logic into a new `handle_get_blocks` function, which pollutes the diff. I figure this is the cleanest solution though.

______
*: I only tested this with a stressnet wallet, which modifies the way the wallet calls `/getblocks.bin`. It's possible the issue doesn't surface with the current release branch wallet, which would explain why this wasn't caught prior. Either way, it's an unexpected issue.
