# Original Description
doInit() took a `ssl` argument and never read it, leaving wallet2::init()'s ssl_options at its default of e_ssl_support_autodetect. Autodetect opens with a real TLS handshake, which over Tor/I2P buys nothing (the transport already encrypts and authenticates) and costs a round trip, or a second connection through the proxy when the daemon does not speak TLS and the client retries in the clear.

TLS is now skipped for .onion/.i2p addresses rather than wherever use_ssl is false. The flag defaults to false, so it cannot be told apart from a caller that said nothing: monero-gui passes the literal and has no SSL setting to override it, so keying off the flag would leave its users on https daemons unable to connect. Setting use_ssl, or using an https:// address, still asks for the handshake and reaches a TLS-only daemon there.

trusted_daemon is passed explicitly because ssl_options follows it. It had been left at wallet2's default of true, briefly marking remote daemons trusted for the daemon height queries doInit() makes before correcting the flag.

worth saying: 
- An explicit `https://` daemon address still gets a handshake attempt on `.onion`/`.i2p`, so a TLS-only daemon stays reachable there.
- A TLS-only daemon on `.onion`/`.i2p` addressed *without* `https://` (e.g. `host.onion:443`) will no longer be reached. Autodetect exists because you cannot know whether an endpoint speaks TLS without trying, so every version of this has that edge.
- `use_ssl` has no effect on clearnet (both values yield autodetect) so unticking an SSL toggle (Cake has one) does not stop the handshake attempt there. Honouring it would need the API to tell an explicit `false` apart from the default, which is worth doing separately.
- `WalletManagerImpl::setDaemonAddress()` still autodetects. It has no `use_ssl` parameter at all, so any change there is a policy choice rather than honouring an argument.

Closes #10992
