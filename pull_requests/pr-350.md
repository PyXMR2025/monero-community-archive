# Original Description
This includes a saner check that FCMP++ compatible wallets *must* point to FCMP++ compatible daemons even before the fork. Recall they must do so in order to sync the tree.

Note: we should expect **all** FCMP++ compatible daemons to return `daemon_hard_forks` to the `get_version` RPC, so we can get rid of all the logic handling the case when it's empty.

## j-berman | 2026-05-05T17:26:39+00:00
The benefit of checking the full hf table is that we can check if the first fork unknown to us has passed. This is useful because we've been using (and plan to use) a double fork pattern (i.e. 2 forks in rapid succession). If we were to only use the last fork height, then we could incorrectly assume the fork has yet to pass, even though the first fork *has* passed (i.e. the logic would be broken for the period between first fork and second fork).

An alternative is the client could include its highest fork version in the request, and the daemon could respond with its next highest fork version and fork height (or the same if the client's requested is also highest, or lower if the daemon's known highest is lower). I figured including the full hf table is relatively insignificant overhead and enables flexibility in this logic if we want to make some change client-side.
