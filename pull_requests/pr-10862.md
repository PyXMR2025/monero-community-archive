# Original Description
Fixes #10032

## What changed
- reconnect the wallet daemon HTTP client before the first `/sendrawtransaction` in `wallet2::commit_tx`
- keep vector submission to one reconnect per batch, then reuse the fresh connection for the rest of the batch
- add unit coverage with a fake daemon HTTP client to lock the disconnect/connect/submit order

## Why
#10032 reports long wallet operations finishing tx construction, then failing broadcast with `no_connection_to_daemon` before reconnecting right after. The HTTP client only auto-connects when it already knows the socket is disconnected, so a stale-looking connection can still be reused for the submit path

This does not retry after a failed submit, so it avoids re-broadcasting a tx that may have reached the daemon already
