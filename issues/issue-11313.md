# Original Description
Currently if the database is corrupted, the only solution is deleting the database and resynchronize. This is not a issue if the user has fast internet, but it is going to be painful for user with low-end machines and slow internet. --db-salvage almost only works if monerod db is already running on safe mode. Although the database is corrupted, most blocks are still accessible and intact. The reconstruction feature should rescan the database on a low level, start from the genesis block, check hashes and verify the integrity of blocks. It should stop at the highest trustworthy block. Then construct a new database based on those verified blocks, delete the old database. The next synchronization should start from that reconstructed height instead of from 0.

# Discussion History
## hyc | 2026-09-14T14:40:56+00:00
The idea sounds appealing, but in practice it's quite resource-intensive. Even the location of the genesis block in the DB isn't known, so every page of the DB must be searched to find it. And then the entire DB must be searched again to find a block whose hash points to its predecessor. It's an O(n^2) task; even on a slow network a full resync will probably be faster. And the only way to know you're done is when a complete scan of all the pages doesn't find any other blocks that point to the last one you found.

Also data from reorg'd blocks may still be present in the DB, so you may find a block that belongs to a dead chain. So even when your scan of the entire DB doesn't find any more succeeding blocks, you have no way of knowing if that's because you're on the longest chain, or because you followed a dead/reorg'd chain. The only way to know would be to scan every DB page exhaustively, and instead of stopping at the first found block that matches a preceding block hash, continue to search for all matches. And most of the time there would only be one match, so you'd be doing a bunch of scanning that will never return any other results.
