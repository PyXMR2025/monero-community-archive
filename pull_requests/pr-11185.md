# Original Description
fixes #9332

`Wallet::store()`, `WalletManager::closeWallet()`, transaction creation, transaction broadcast, and file-only transaction saving could run while refresh was mutating wallet state

suspend the active refresh, wait for wallet state to settle, perform the operation, then restore the previous auto-refresh state. synchronous refresh and rescan calls return false if an operation interrupts them, without emitting `refreshed()` for that attempt. queued refresh and rescan requests stay pending until they can run

operations that would acquire another refresh lock from a refresh callback or another guarded wallet operation return an error instead of risking reentrant or cross-wallet deadlocks. file-only commits remain allowed when the same wallet is already serialized

tests:
- full GCC release build
- full `libwallet_api_tests` with GCC and Clang (55/55)
- full `unit_tests` (1308 passed, 2 skipped)
- focused concurrency repetitions and mutation checks

Same race still open on unguarded entry points: `addSubaddressAccount`/`addSubaddress` write `m_subaddresses` via `expand_subaddresses` (wallet2.cpp L1673) while the refresh thread reads/writes it in `process_new_transaction` (`unordered_map`, so UB); `scanTransactions` appends to `m_transfers`; `rescanSpent` fills `spent_status` from `m_transfers.size()` during its RPC loop and then indexes it up to the *current* size (OOB read if a transfer was appended meanwhile); `importKeyImages` rewrites key images/spent flags across an RPC. Readers (`balance`, `exportKeyImages`, `createWatchOnly`, `TransactionHistory::refresh`) iterate `m_transfers`/`m_payments` under the same reallocation hazard `store` had. If those are deferred, please list the covered set in the description.

## thomasbuilds | 2026-09-15T13:50:22+00:00
From `refreshAsync`/`startRefresh` this is set without `m_refreshMutex`, while the thread checks the predicate under it and then blocks: a request landing between check and block is still lost (the flag only covers a busy thread), and with interval 0 only a later request wakes it. Taking `m_refreshMutex` here isn't an option (`release()` already holds it, and it's held across `doRefresh`); a dedicated mutex+CV for the request flag, with `m_refreshMutex` only around `doRefresh`, fixes it.

## thomasbuilds | 2026-09-15T13:50:22+00:00
`m_refreshInterrupted` is set when an interrupting lock is *requested*, so a refresh that already completed (request landed after its last batch) is reported as deferred: sync `refresh()` returns false with "Refresh interrupted…" and `refreshed()` is not emitted; a background pass silently drops its `refreshed()`. `wallet2::refresh` reporting whether its loop was actually cut short would give the right signal.
