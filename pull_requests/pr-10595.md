## iamamyth | 2026-05-18T16:35:59+00:00
I don't particularly like the IO pattern: Where possible, operating on streams tends to clarify intent, perform a lot better, and greatly simplify testing. Here, for example, the function accepts a path, then reads the file into a string, only to wrap the string in a stream; having the function accept a stream cuts out clutter (you can, of course, offer a path-based version which delegates the heavy lifting to the stream implementation).

## iamamyth | 2026-05-18T16:36:31+00:00
URLs can contain `;`, so I'd suggest flipping the order and placing the checksum first (you could, instead, pick an alternate separator, like space, but that might lend itself to typos).

## iamamyth | 2026-05-18T16:43:07+00:00
If you were to stream the file here, you could relax the size constraint (e.g. 10MB shouldn't be a big deal). Also, though, I think this filesize paranoia misses a key point from the earlier discussion: If you require all hosts to offer *the same file*, and apply a DNS-based quorum rule, it's pretty hard to cheat, as the DNS record can include the filesize, and someone has to compromise a lot of DNS records. A file size failsafe seems OK, but very much a last resort (sadly, HTTP won't necessarily tell you the size in advance, so forcing the size to be available via DNS helps).

## iamamyth | 2026-05-18T16:47:35+00:00
Minor addendum: If you want to let alternate hosts use different banlists, you can still include the sizes in the DNS record, which helps with fail-early behavior (really, the HTTP server should be setting content-length for the whole file, but you can't guarantee it).
