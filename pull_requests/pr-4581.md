# Original Description
### Problem

Both `DaemonManager::start()` and `P2PoolManager::start()` launch their child via `QProcess::startDetached()` (and monerod also gets `--detach` on Unix), so the `QProcess` instance never tracks the real child:

1. The `readyReadStandardOutput`, `readyReadStandardError`, and `stateChanged` connections in `DaemonManager::start()` never fire. The daemon console therefore shows nothing and `daemonStopped()` is never emitted on exit.
2. Shutdown falls back to `pkill` / `taskkill /F /IM`, which kills **every** monerod / p2pool on the host, including a user's systemd-managed monerod or a separately launched p2pool.

### Fix

- `setProgram` / `setArguments` + `start()` + `waitForStarted()` on the owned `QProcess` in both managers.
- Drop `--detach` on Unix. `--non-interactive` is already passed unconditionally and is what keeps monerod off stdin.
- Move the `stateChanged` `connect()` above `start()` so early state transitions aren't missed.
- Targeted shutdown on the owned process: daemon calls `kill()` under `m_daemonMutex`; p2pool calls `terminate()`, then `waitForFinished(5000)`, with `kill()` as a fallback.
- `m_daemonMutex` is now `mutable` so the `const` `stopWatcher()` can lock it.

### Notes

- No QML or public API change; `Q_INVOKABLE` signatures are unchanged.
- On Windows the previous code already omitted `--detach`, but it still used the static `startDetached(program, args)` overload, so the signals were broken there too. This change fixes both platforms uniformly.
- `DaemonManager` and `P2PoolManager` are stack-local in `main()`, so on a graceful application exit `~QProcess` now sends `SIGKILL` / `TerminateProcess` and waits for any still-running child. Previously the unowned child leaked.
- A hard crash of the GUI (SIGKILL, segfault) still orphans the child on both platforms: Qt's `QProcess` does not associate children with a Win32 Job Object on Windows, nor call `prctl(PR_SET_PDEATHSIG, ...)` on Linux.
