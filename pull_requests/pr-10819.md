This approach somehow looks unfortunate:

You have the Wallet API which generates error codes. Then you translate those to exceptions. Then you catch these exceptions and translate them to error codes, a process that throws them *again* and catches them *again*,  to give the error codes finally back as result of RPC calls.

This sure avoids special cases where code does "naturally" throw exceptions that you have to catch to deal with them, but I still ask myself if a simple method (not even a macro) that translates Wallet API error codes to RPC call result codes would somehow be possible, and you would replace references to the macro with calls to this code translation method.

Furthermore, this macro looks like about 50 lines of code long, and you call it about 50 times or so, so this will expand to roughly 2500 lines of code to compile. A simple code translation method on the other hand, if it's feasible, would do this in 50 lines *once*.

## rbrunner7 | 2026-08-06T12:04:25+00:00
Well, I don't want to turn your Wallet RPC migration to the Wallet API into an almost endless job, but I do feel that here and maybe also in quite a number of other places you "walked only about half the way" and missed a chance.

The Wallet API method `thaw` already returns an error if the string is not valid hex, so that now gets checked twice, here and inside the method. The missed chance: There is no `ExtendedStatus_WrongKeyImage`, and thus is not possible for the `thaw` method to return a detailed reason what went wrong, and in turn not possible for the RPC server to return its specific `WALLET_RPC_ERROR_CODE_WRONG_KEY_IMAGE` if it did not check itself as well.

It's not only the question to eliminate the conversion to hex check here, it's also about all the other callers of `thaw` that we may get over time: They all would also profit from the method setting an extended status.

The `ExtendedStatus` enum currently covers about 20 out of 50 or so possible errors, so it's possible we have about 30 cases where a Wallet API method could, ideally, use the new extended status mechanism to return more detailed error info, but does not yet.
