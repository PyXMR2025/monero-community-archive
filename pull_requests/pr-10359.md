# Original Description
Builds on top of:
- #10358

This PR introduces the Rust FFI, as well as a function to take 32 bytes -- the byte representation of a Selene scalar -- and convert the byte representation into the Selene scalar object used in the Rust code.

Recall "Selene" is the name of the curve in the tower cycle towering Ed25519: https://gist.github.com/tevador/4524c2092178df08996487d4e272b096 . As part of constructing the curve tree merkle tree, we take Ed25519 points and convert them to Selene scalars (the leaves of the tree are composed of Selene scalars).

The `selene_scalar_from_bytes` function introduced in this PR takes the 32 byte representation (that we derive from ed25519 points on the C++ side), and produces the Selene scalar Rust FFI compatible object that we use in future Rust FFI functions when constructing the curve tree merkle tree.

_____

Trail of Bits and Cypher Stack audited an earlier state of this PR. Both pointed out a fragile memory layout assumption of the FFI-compatible Rust objects. See Cypher Stack's [section 11](https://github.com/cypherstack/fcmp-impl-audit/blob/d7de33d08c48a3c249629e47f71ea72c938a3404/FCMP_Code_Implementation_Audit.pdf), and the Trail of Bits audit [pages 18-19, and 23](https://github.com/trailofbits/publications/blob/master/reviews/2026-07-magicgrants-monerofcmp++crypto-securityreview.pdf). This was remediated in the latest version of the code (with [this change](https://github.com/j-berman/monero/pull/20) that uses static asserts on size and alignment on both sides of the FFI boundary).

Trail of Bits reviewed the remediation and concluded that their concern was "partially resolved," and encourages improving the robustness of the API further (page 23). The comment included in this PR is the justification for leaving it as is:

> Is there a reason not to hardcode the alignment?

It's platform dependent (32-bit platforms will be different from 64-bit e.g.)

> There seems to be an assumption that sizeof(uintptr_t) [C++] == size_of<usize>() [rust].

Rust's unsafe guidelines mentioned the following [here](https://github.com/rust-lang/unsafe-code-guidelines/blob/c138499c1de03b908dfe719a41193c84f8146883/reference/src/layout/scalars.md#isize-and-usize):

> The isize and usize types are pointer-sized signed and unsigned integers. They have the same layout as the [pointer types](https://github.com/rust-lang/unsafe-code-guidelines/blob/c138499c1de03b908dfe719a41193c84f8146883/reference/src/layout/pointers.md) for which the pointee is Sized, and are layout compatible with C's uintptr_t and intptr_t types.

Notably that page was archived as of [this commit](https://github.com/rust-lang/unsafe-code-guidelines/blob/d809f91e62968913d808e53397fbcf7cea762cce/reference/src/layout/scalars.md).

We are relying on the assumption that `uintptr_t [C] == usize [rust]` elsewhere in the FFI.
